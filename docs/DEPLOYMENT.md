# 部署架构与工具说明（从底层到业务）

本文说明本实验项目从**开发机到被试浏览器**的完整链条，并尽量从**操作系统、进程、网络、协议**等底层角度解释各环节使用的工具**在解决什么问题**。

---

## 1. 为什么要分层理解

软件部署不是「点一下部署」魔法，而是一串**约束**叠加的结果：

- **机器层面**：CPU 只执行二进制指令；要有操作系统调度进程、管理文件与网络套接字。
- **隔离层面**：同一台宿主机上跑多个应用时，需要**进程边界**或**容器边界**，避免依赖冲突与文件系统互相踩踏。
- **网络层面**：被试的浏览器与服务器可能相隔半个地球，中间经过 DNS、负载均衡、TLS 终结，应用必须监听**平台指定的端口**并讲**标准 HTTP**。
- **数据层面**：实验记录必须**持久化**在数据库进程管理的磁盘结构上，而不是只存在 Web 进程的内存里。

下面先给一张**逻辑分层图**，再按时间顺序走一遍部署流，最后按**工具**做词典式说明。

## 2. 分层模型（本项目的简化视图）

```
┌─────────────────────────────────────────────────────────────┐
│  被试浏览器：HTTP(S) 客户端、TLS、DNS 解析                    │
└────────────────────────────┬────────────────────────────────┘
                             │ TCP + TLS（加密 HTTP）
                             ▼
┌─────────────────────────────────────────────────────────────┐
│  Railway 边缘：证书、域名 → 反向代理 → 转发到容器内端口        │
└────────────────────────────┬────────────────────────────────┘
                             │ 通常转发到容器内 process.env.PORT
                             ▼
┌─────────────────────────────────────────────────────────────┐
│  容器内：Linux 用户态进程                                   │
│  └── Node.js 运行时（V8 引擎 + libuv I/O 线程池）            │
│       └── 单进程：Express（HTTP 路由）+ 静态 dist + /api/*     │
└────────────────────────────┬────────────────────────────────┘
                             │ TCP（常为本机或内网）
                             ▼
┌─────────────────────────────────────────────────────────────┐
│  PostgreSQL 服务进程：监听 5432（或平台指定端口），存 WAL/数据页 │
└─────────────────────────────────────────────────────────────┘
```

**要点**：

- **Node 进程**在容器里只是一件「普通」用户态程序：向内核申请端口 `listen()`，对 Postgres 发起 `connect()`。
- **TLS 往往终结在平台边缘**（Railway 一侧），容器内常见的是「已解密后的 HTTP」；对你写的 Express 来说仍是 `req`/`res`，但对外 URL 是 `https://`。

## 3. 端到端时间线（从改代码到被试访问）

### 阶段 A：开发与「可构建产物」

1. 你在本机编辑源码（React、`server.ts` 等）。
2. **`npm install`**：根据 `package.json` 与 `package-lock.json` 把依赖下载到 `node_modules/`。  
   - **底层**：Node 解析依赖树，写大量文件到磁盘；原生模块可能触发 **node-gyp** 编译（本项目以 JS/TS 为主，依赖侧重点是 `pg` 等纯 JS/预编译部分）。
3. **`npm run build`（Vite）**：把 TypeScript/JSX 等**打包、压缩**进 `dist/`（HTML/CSS/JS 资源）。  
   - **底层**：对浏览器而言，最终只需要**静态文件**与**可执行的 JS**；不需要在服务器上跑 Vite 开发服务器。
4. **题池 JSON**：`public/arc_pool_*.json` 在构建时被 Vite 视为 **`public/` 资源**，复制进 `dist/`（或运行时被 Express 静态中间件从磁盘读——取决于配置；本项目生产路径以 `dist` 为主）。  
5. **`build:pools`（仅本地需要时）**：从 ARC 原始大数据生成 `public/arc_pool_*.json`。  
   - **为何不进云端 Docker 构建**：脚本历史上从**项目上一级目录**读 `ARC-AGI * Data`；在镜像里工作目录为 `/app`，上一级没有这些数据，会得到 0 道题。因此**线上依赖已提交到 Git 的 JSON**，而不是在镜像构建时现算。

### 阶段 B：版本控制与「单一事实来源」

6. **`git commit` / `git push`**：把**当前目录树快照**推到 GitHub。  
   - **底层**：Git 存的是**内容寻址的对象**（blob、tree、commit），不是「文件夹拷贝」；`.gitignore` 保证 `.env` 等不会进入对象库。  
7. **GitHub**：托管 **bare repo**，Railway 通过 **Git 协议/HTTPS** 拉取指定分支（如 `main`）。

### 阶段 C：云端构建（Docker 镜像）

8. Railway 检测到 **`Dockerfile`**，用 **Docker BuildKit** 之类引擎按指令构建**镜像**（一组只读层 + 最终文件系统快照）。  
   - **底层**：镜像符合 **OCI** 规范；每层是 **union mount** 上的一层差异；运行时再叠一层可写层成为**容器**。
9. **`Dockerfile` 典型顺序的意义**：  
   - 先 `COPY package*.json` 再 `npm install`：依赖不变时可利用**构建缓存**，少下载。  
   - 再 `COPY . .`：源码与 `public/` 进入镜像。  
   - `RUN npm run build`：在**构建容器**里执行 V8 进程，生成 `dist/`，结果写入镜像层。  
   - **不在此运行 `build:pools`**：避免在缺少 ARC 源数据的环境下失败（见上）。

### 阶段 D：运行与联网

10. **`CMD ["npm", "start"]`**：容器启动时，由 **init 进程**（容器 PID 1）拉起 **npm**，再拉起 **Node 子进程**执行 `package.json` 里的 `start` 脚本。  
11. **`NODE_ENV=production`**：Express/Vite 相关库据此走**生产分支**（例如本项目中：不用 Vite middleware，而用 `express.static(dist)`）。  
12. **`tsx server.ts`**：**tsx** 在运行时把 TypeScript **转译**为可执行代码（或走 esbuild 快路径），无需单独 `tsc` 产出 `server.js`。为放进生产依赖，避免平台 `npm install --omit=dev` 时找不到 `tsx`。  
13. **Express `app.listen(PORT, '0.0.0.0')`**：  
    - **`0.0.0.0`**：绑定**所有网卡**，容器外（Railway 代理）才能连进来；若只绑 `127.0.0.1`，外部无法访问。  
    - **`PORT`**：Railway 注入**非特权端口**；应用必须服从，否则健康检查与公网入口对不上。

### 阶段 E：数据库与业务数据

14. **`pg` 的 `Pool`**：维护一组到 PostgreSQL 的 **TCP 连接**（可复用），执行 SQL。  
    - **底层**：Postgres 是独立进程，通过 **C/S 协议**（基于 TCP）通信；连接串 `DATABASE_URL` 里含主机、端口、库名、用户、密码（常带 `sslmode`）。  
15. **启动时建表**：`server.ts` 在首次连接后执行 `CREATE TABLE IF NOT EXISTS`，保证**空库**也能启动。  
16. **持久化**：提交的数据写入 Postgres 数据目录（由平台管理）；**容器重启**不会丢库，除非删库服务。

### 阶段 F：被试访问

17. 浏览器解析 DNS → TLS 握手 → HTTP GET `/`。  
18. Railway 把请求转到你的 Node 进程；静态页由 **Express 静态中间件**返回；`/api/*` 由路由处理。  
19. 前端再通过 **fetch** 调同源 `/api/...`，Cookie/策略由你当前实现决定（本项目多为 JSON API）。

## 4. 工具词典：是什么、在栈的哪一层、为什么用

### 4.1 Git

- **是什么**：分布式版本控制系统；核心是不可变 **commit 图**与**内容寻址存储**。
- **层**：开发与发布衔接层（在「源码」与「托管平台」之间）。
- **为什么用**：可复现、可回滚、可审计；与 GitHub 配合做 **CI/CD 的触发源**（push → 构建）。

### 4.2 GitHub

- **是什么**：Git 远程托管 + 权限 + Web API。
- **层**：托管层（不在你的服务器上）。
- **为什么用**：Railway 等平台通过 OAuth 拉仓库；**Private** 降低实验材料与实现细节泄露风险。

### 4.3 Node.js

- **是什么**：基于 **V8** 的 JavaScript 运行时 + **libuv**（事件循环、线程池、异步 I/O）。
- **层**：用户态进程内的运行时（容器里跑的就是一个或多个 Node 进程）。
- **为什么用**：前后端工具链统一；Express、`pg`、Vite 均在 JS 生态。

### 4.4 npm 与 package.json / package-lock.json

- **是什么**：包管理器；清单文件与**锁定解析结果**的文件。
- **层**：构建时依赖解析（磁盘上形成 `node_modules/` 有向图）。
- **为什么用**：可重复安装；`lock` 文件减少「我机器能跑、你机器不能跑」。

### 4.5 TypeScript 与 tsx

- **TypeScript**：带类型的 JS 超集，默认需编译。
- **tsx**：在 **Node 里直接执行 TS** 的启动器（内部依赖快速转译）。
- **层**：源码 → 可执行之间的桥梁（开发 `npm run dev` 与生产 `npm start` 都用得到）。
- **为什么用**：服务端保持 TS 而不维护一份单独的编译产物；**生产依赖中包含 tsx** 是为了兼容平台默认不装 devDependencies 的情况。

### 4.6 Vite

- **是什么**：以 **esbuild** 等为底层的现代打包器；开发时提供 Dev Server，生产时 `vite build` 输出静态资源。
- **层**：构建期工具（构建容器内运行，运行期不常驻）。
- **为什么用**：快速 HMR（本地）、生产 tree-shaking 与 chunk 分割；输出适合浏览器缓存的哈希文件名。

### 4.7 Express

- **是什么**：极简 HTTP 框架：路由、`req`/`res`、中间件链。
- **层**：应用层 HTTP（在 Node 的 `http` 模块之上）。
- **为什么用**：同一进程同时服务 **静态前端** 与 **REST 式 API**，部署模型简单。

### 4.8 PostgreSQL 与 node-pg（`pg`）

- **PostgreSQL**：持久化引擎：进程 + 共享缓冲区 + WAL + 磁盘上的堆文件与索引。
- **`pg`**：Node 的 Postgres **协议客户端**。
- **层**：传输层 TCP 之上的数据库协议；对你代码暴露为 SQL + JS 类型。
- **为什么用**：多被试并发写入、事务、查询分析（Metabase 等 BI 工具生态成熟）。

### 4.9 Docker 与 Dockerfile

- **Docker**：把**应用及其依赖文件系统**打成**镜像**，运行时成为**与宿主机隔离**的容器（namespace/cgroups 等由 Linux 内核提供）。
- **Dockerfile**：声明式构建步骤。
- **层**：介于「操作系统」与「你的应用」之间的**打包与隔离**层。
- **为什么用**：Railway 构建环境一致；避免「平台默认 Node 版本/命令猜错」；本地可用近似相同镜像调试。

### 4.10 Railway

- **是什么**：PaaS：编排 **构建 → 部署 → 网络入口 → 密钥注入 → 托管数据库**。
- **层**：平台层（你不再自管虚拟机、证书、部分网络）。
- **为什么用**：快速获得 **HTTPS 公网 URL** 与 **托管 Postgres**；适合研究型项目冷启动。

### 4.11 railway.toml（可选）

- **是什么**：**配置即代码**：启动命令、健康检查路径等。
- **层**：平台声明层。
- **为什么用**：避免只在网页上配、丢失记录；与仓库同步，可 code review。

### 4.12 环境变量（GEMINI_API_KEY、DATABASE_URL、NODE_ENV、PORT）

- **是什么**：进程启动时由父进程（容器编排器）注入的 **key=value** 字符串，进入 `process.env`。
- **层**：操作系统进程环境块（POSIX `environ`）。
- **为什么用**：**密钥与连接串不进镜像、不进 Git**；同一镜像换变量即可连不同库。

## 5. 本题池（`build:pools`）与仓库策略

| 事项 | 说明 |
|------|------|
| 脚本期望的 ARC 源数据 | 默认在**项目父目录**下的 `ARC-AGI 1 Data`、`ARC-AGI 2 Data`（本机目录布局）。 |
| Docker 内 | `/app/..` 为根文件系统，无上述目录 → 过滤后 0 题。 |
| 线上策略 | **将已生成的 `public/arc_pool_*.json` 提交到 Git**；镜像构建只跑 `vite build`。 |
| 更新题池 | 在本机有 ARC 数据时运行 `npm run build:pools`，再 commit/push JSON。 |

脚本中若检测不到源数据但 `public/` 已有合法题池，会**跳过重写**（防止误用在 CI 时直接失败）；但 **Dockerfile 已省略 `build:pools`**，以缩短构建时间。

## 6. 健康检查与「为什么用 /api/results」

Railway 在容器启动后会按配置对路径发起 HTTP 请求，期望 **2xx**。

- 选 **`/api/results`** 的原因：不依赖前端路由；由 Express 直接返回 JSON，**轻量**；能间接证明「Node 已监听且数据库查询路径可走」（若库未连上，可能 5xx，部署会失败提示你修 `DATABASE_URL`）。

## 7. 安全与边界（与部署相关的底层点）

1. **TLS**：对外 HTTPS 保护**传输中**窃听；不替代服务器端访问控制。
2. **密钥**：`GEMINI_API_KEY` 仅在服务端用于调用 Google API；勿下发给浏览器。
3. **`DATABASE_URL`**：拥有它的人等同数据库账号权限；只放在平台变量，勿发给被试。
4. **公开 `/api/*`**：当前为研究便利默认开放；若上公网，需评估是否加 **鉴权、IP 限制、或独立管理域名**。

## 8. 小结表

| 工具 | 主要解决的底层问题 |
|------|-------------------|
| Git / GitHub | 可复现的源码版本与协作 |
| Docker | 文件系统与依赖的一致快照 + 进程隔离 |
| Node / npm | 统一运行时与依赖安装 |
| Vite | 浏览器可执行的静态资源生成 |
| tsx | 无预编译步骤运行 TS |
| Express | HTTP 语义（方法、路径、头、体）的服务端实现 |
| PostgreSQL | 持久化与并发下的关系型数据 |
| pg | TCP 上 Postgres  wire protocol 的客户端 |
| Railway | 构建编排、HTTPS 入口、密钥注入、托管 DB |

---

若你更换平台（如 Render、Fly.io），**容器内行为与 Node/Postgres 关系不变**，变的多是：**谁注入 PORT、连接串主机名、TLS 与构建缓存策略**。理解上述分层后，迁移主要是改平台配置而非改业务逻辑。
